# 踩坑记录

开发过程中真实踩到的坑。每条都是：**现象 → 原因 → 处理 → 教训**。
（这份记录的重点不是"实现了什么"，而是"错在哪、怎么定位、怎么修的"。）

---

## 一、Agent 循环

### 1. `trace.append` 缩进跑进了 `except` 分支 → 轨迹表里一条模型记录都没有

**现象**：执行轨迹表打出来只有工具行（全是 `—`），模型调用一行都没记。

**原因**：`trace.append({...})` 和 `msg = resp.choices[0].message` 这两行缩进是 12 个空格，
落在 `except` 分支里了。而 `try` 里成功会 `break` 跳出循环——
**两行成了死代码，永远不会执行。**

```python
for attempt in range(3):
    try:
        resp = client.chat.completions.create(...)
        break
    except Exception as e:
        if attempt == 2:
            return f"接口连续 3 次调用失败：{e}", log
        time.sleep(2 ** attempt)
        trace.append({...})        # ← 12 空格，跑进 except 里了
```

**处理**：挪到 `for attempt` 循环**外面**、与 `msg = ...` 平级。

**教训**：**缩进错误不会报语法错。** 唯一能发现它的办法是"看输出对不对"——
如果我没有先看一眼轨迹表，这个 bug 会一直藏着。

### 2. `print_trace(trace, ...)` 里的 `...`

**现象**：
```
TypeError: unsupported format string passed to ellipsis.__format__
```

**原因**：写代码时随手打了个 `...` 占位，忘了填。
`...` 在 Python 里是合法对象（`Ellipsis`，相当于 `None` 的亲戚），
**所以既不报语法错也不报 NameError**，一路跑到格式化字符串时才炸。

**处理**：改成真正的耗时值，并在 `main()` 里 `t_start = time.time()` 起表。

**教训**：`...` / `pass` / `TODO` 这些占位符编译器都放行。
**占位符必须当天填掉，不然它就是个定时炸弹。**

---

### 3. `u.prompt_cache_hit_tokens` 不是 OpenAI 标准字段

**现象**：要换成别的模型/别的服务商时，这行会 `AttributeError`。

**原因**：`prompt_cache_hit_tokens` 是 **DeepSeek 的扩展字段**，OpenAI 官方 SDK 的 `usage` 对象里没有。

**处理**：全部改 `getattr(u, "prompt_cache_hit_tokens", 0)`，`prompt_tokens` / `completion_tokens` 一起兜。

**教训**：**可观测性是附属功能，不该拖垮主流程。**
统计不到就记 0，不能让"记日志"这件事把"回答问题"搞崩。

（同一个坑的另一半：读的时候用 `r.get("cache_hit", 0)` 有兜底，写的时候却用 `r["cache_hit"]`——
**读写不对称**。要么两边都兜底，要么两边都不兜。）

### 4. `"step": 0` 和 `None` 混用

**现象**：`do_generate_quiz` 里那两条 trace 记录（"检索(出题)"和"生成题目"）
在补号循环里捞不到，`step` 一直是占位值。

**原因**：占位符一开始写的是 `"step": 0`，但补号循环判断的是 `if rec["step"] is None`。
而且 `0` 是合法的步数（第 0 步？），**语义上就错了**。

**处理**：占位统一用 `None`，判断统一用 `is None`。4 处成对修改，漏一处就出错。

**教训**：**哨兵值（"还没有值"）永远用 `None`，不要用 `0` / `-1` / `""`。**
用 `0` 的话，你分不清它是"没填"还是"填了 0"。

### 5. `search()` 引用了列表推导式的私有变量

**现象**：
```
NameError: name 'idx' is not defined. Did you mean: 'ide'?
```

**原因**：写成这样了：
```python
for ide, sc in top:
    parts = [f"块 #{idx}（来自 {chunks[idx]['source']}..." ]   # ← idx 是哪来的？
```
`idx` 是**上面那个列表推导式里的变量**。Python 3 里列表推导式是**独立作用域**，
出了 `]` 就消失。等价于：
```python
x = [i * 2 for i in range(3)]
print(i)          # NameError
```

**处理**：删掉外层 for，恢复列表推导式并正确解包：
```python
parts = [
    f"块 #{idx}（来自 {chunks[idx]['source']}...）"
    for idx, sc in top
]
```

**教训**：**这个 bug 还藏着第二个问题**——就算名字写对了，
`parts = [...]` 写在 `for` 循环体里是**覆盖**不是**累积**。
`top` 有 3 个元素，最后只会剩最后一块，模型只拿到相关度最低的那 1 块。
**要累积的地方写 `=` 而不是 `+=` / `.append()`，是同一类错误的两种表现。**

## 二、引用校验

### 6. `return` 缩进错 → 只查了 1/3 的引用，却报告"0 违规"

**现象**：引用校验看起来一切正常，输出 `引用校验：3 处引用，0 处无效`。

**原因**：`return` 落在 `for n in cited:` **循环体内**：
```python
for n in cited:
    ...
    return "\n".join([head] + lines), invalid      # ← 第一轮就返回了
```
所以三处引用**只查了第一处**，后两处根本没进循环——
"0 违规"是因为**压根没查**。

**处理**：`return` 提到循环外。

**教训**：**"0 违规"有两种可能：真的没问题，或者没查。**
一个检查函数报告"全通过"时，第一件事是确认它**真的跑了**——
用探针实测（打印 `seen` 的键集合、打印 `total`）比看返回值可靠。

---

### 7. 想校验"引用内容是否与原文一致"，被自己的实测否掉了

**现象**：我做了一版 L3 校验，用"引用标记前 80 个字的字符重合度"判断模型有没有瞎引。
跑出来全部只有 **4%~9%**——按这个数字，模型几乎每句话都在编。

**但这是误报。** 两个原因：

1. **那 80 个字是模型自己的过渡句**，不是原文。比如它写"资料明确给出了对比（块 #53）"，
   真正的原文引用在标记**之后**，不在前面。
2. **模型是改写式引用**：原文"同一专题的题共享解题模式"，它写"同类题共享解题模式"。
   字符级比对必然全不匹配。

**处理**：**这个方案砍掉。** 唯一可行的版本是"只检验显式引号内的内容是否逐字出现在被引块"，
收益低、误报多，不值得做。

**教训**：**测量结果是"看起来很糟"时，先怀疑测量方法，再怀疑被测对象。**
我如果直接信了这 4%，就会写一个天天误报、把模型搞得无意义返工的校验器。

**最终定位**：引用校验负责**出处真实**，不负责**内容真实**。这个边界要主动说清楚。

### 8. 想在散文里校验文件名 → 两次尝试都失败

**背景**：引用校验只能查"块号在不在本次检索结果里"。
但模型可能**块号给对、文件名给错**（把见过的 `#37 → 算法与数据结构笔记` 和
`#27 → Python语言笔记` 交叉配对）。我想加一层"文件名交叉验证"。

**第一次尝试（全局收集）**：
```python
claimed = {f for f in FILE_RE.findall(answer) if f in valid_files}
```
**必然误报**：一整篇回答里所有文件名都被收进同一个集合，
检查 `#37` 时会把 `#4` 的文件名也算进来。

**第二次尝试（按块号开窗）**：加 `WINDOW = 40`，只取块号前后 40 字。
**仍然误报**：块号 `#37` 和 `#4` 在回答里只隔 30 个字，
窗口 `[43-40 : 47+40] = [3:87]` 的起点落进了 `#37` 的地盘，把它的文件名捞了进来。

**第三次尝试（窗口不跨界）**：遇到上一个块号的结尾 / 下一个块号的开头就截断。
**还是误报**：`#4` 的窗口左边界被截到 13，而 13~43 这段里正好躺着 `#37` 的文件名。

**结论**：**散文式回答里没有可靠的归属边界。**
块号是结构化的（`块 #37` 这个 token 唯一确定），所以能校验；
文件名是散落在句子里的自然语言，**它跟哪个块号是一对，只有模型自己知道**。

**换方案**：让模型在结尾输出一个**结构化的配对清单**：
```
参考来源：
块 #37 = 算法与数据结构笔记_clean.txt
块 #4 = Python语言笔记_clean.txt
```
用正则 `^\s*块\s*#\s*(\d+)\s*[=＝:：]\s*([\w\u4e00-\u9fff\-]+\.(?:txt|md))\s*$` 抓。
探针实测：真模型输出配对全部正确，注入 5 种错误能抓到 4 种。

**但最后没上线**：要求模型多输出这一段，每次多花 60~100 个输出 token，
而实测 5 个查询 **0 次张冠李戴**——**零收益。**
按我自己在"术语表"上学到的原则：**测不出收益的复杂度就是负债，先不加，真遇到再加。**

**教训**：**遇到"想校验自然语言"的需求，第一反应应该是"能不能让模型输出结构化数据"。**
把不可校验的散文变成可校验的键值对，比写更复杂的正则便宜得多。

## 三、终端排版

### 9. `len()` 数不出中文占 2 列 → 表格歪了很久没被发现

**现象**：执行轨迹表格始终对不齐。实测各行的**显示宽度**：

| 行 | 显示宽度 |
|---|---|
| 表头 | **69** |
| 模型行 | 63 |
| 工具行 | **58** |
| 另一模型行 | 64 |

**四种不同的宽度，怎么可能对齐。**

**原因**：`f"{'用途':<22}"` 里的 `22` 是**补齐到 22 个字符**，不是 22 列。

```python
len("模型决策")        # 4      ← 字符数
# 但它在终端里占 8 列     ← 显示宽度
```

所以：
- 表头少算了 **11 格**（11 个汉字）
- 工具行（只有 `—`）少算 **0 格**
- 模型行（4 个汉字）少算 **4 格**

**表头和数据行差 11 格，但它俩的 `len()` 都是 58，看起来一模一样。**

**处理**：
```python
import unicodedata

def dwidth(s):
    """字符串占几列：中日韩全角字算 2，其余算 1"""
    return sum(2 if unicodedata.east_asian_width(c) in "WF" else 1 for c in str(s))

def pad(s, n):
    """左对齐补到 n 列（中文按 2 列算）"""
    s = str(s)
    return s + " " * max(0, n - dwidth(s))
```

**教训（三条，都吃过亏）**：

1. **`len()` 永远查不出这个 bug。** 报 58 对 58 的时候，实际是 58 对 69。
   验证对齐必须用 `dwidth()` 或肉眼看截图。
2. **表头和数据行必须走同一个函数。** 我中间有一版表头用 f-string、数据行用 `pad`，
   两套算法必然错位——"同一个列，三行落在 20 / 22 / 18 三个位置"。
3. **只要列里可能含中文，`f"{...:<N}"` 一个都不能用。**
   左对齐、右对齐都行，但**"数显示宽度"这件事删不掉**。

## 四、BM25 / 中文检索

### 10. 查一个完全不存在的东西，分数比真实查询还高

**现象**：查询「完全不存在的词xyz」拿到 **6.42 分**，
而查询「异步」的最高分只有 **2.15**。**不存在的词排第一。**

**原因**：中文 BM25 的经典坑。查询被分词成：
```python
['完全', '不', '存在', '的', '词', 'xyz']
```
**六个 token 全是高频虚词。** BM25 是"查询里每个词在每个文档上的得分之和"——
虚词虽然单项分低，但**到处都有**，加起来就超过了一个真实术语。

**处理**：建 `停用词表.txt`，**239 个词**（71 个符号 + 72 个单字虚词 + 96 个多字虚词）。
过滤后：
```python
['完全', '不', '存在', '的', '词', 'xyz']  →  ['存在', '词', 'xyz']
```

**教训**：**高频 ≠ 该过滤。** 词频统计里 `'的'` 出现 454 次、`'，'` 452 次（该删），
但 `'项目'` 105 次、`'Python'` 89 次、`'算法'` 44 次（**绝对不能删**）。
判断标准是**区分度**，不是频次。

### 11. 加了自定义词典，所有分数突然全变 0

**现象**：把「双指针」加进 jieba 词典后，**检索结果全变成 0 分**。

**原因**：**索引和查询用了不同的分词。**
索引是在加载词典**之前**建的，用的是 `['双','指针']`；
而查询时词典已经生效，切成 `['双指针']`。
**两边词表对不上，BM25 一个都不匹配。**

**顺带发现一个更隐蔽的顺序问题**：`jieba.load_userdict` 必须在**任何** `cut` 之前调用，
否则词典**静默不生效**——不报错，只是没作用。

**处理**：确立顺序铁律：

```
加载用户词典 → 切分 → 分词（索引和查询共用同一个函数） → 建 BM25
```

**教训**：**索引和查询必须共用同一个 `tokenize` 函数**，
不然改了任何一处（加词典、改停用词）都会**静默**变差——不报错，只是结果悄悄变烂。

### 12. 手工整理的术语表，实测零收益

**背景**：中文检索的经典问题是「双指针」会被切成 `['双','指针']`，
只有"指针"有区分度。我手工从三份资料里用 TF-IDF 筛出 **35 个术语**做成 `术语表.txt`。

**测量**：严格 top-1 准确率（必须是第一名的那个块才算对）

| 方案 | 严格 top-1 |
|---|---|
| 不带术语表 | **6 / 6** |
| 带术语表 | **6 / 6** |

**零收益。**

**原因**：**BM25 的 IDF 项已经编码了"稀有词更重要"这个直觉。**
手工加词典是在重复加权——而且加进去的词权重被抬高后，
反而可能**淹没**真正有区分度的词。

**处理**：**不加。** 术语表保留为可选，默认不启用。

**教训**：**这是整个项目里我最满意的一个决定。**
它证明的不是"我会写检索"，而是**"我会测量，并且敢砍掉自己刚写的东西"**。

顺带一提：我另外还写了一版自动挖术语的脚本（`挖术语.py`），
产出的是 `你的数据结` → `你/的/数据/结`、`厂日常实` 这种乱码——
因为固定长度切片忽略了词边界。**真正的术语提取需要新词发现（PMI / 内聚度），不是几行脚本能做的。**
这个失败我也留着，因为它说明我知道"什么该用算法、什么该用测量"。

## 五、命令行 / 环境

### 13. `main()` 里的四个 bug —— 根因是"顺序错了"

我在 `main()` 里想一次干三件事（定数据源 / 解析块大小 / 解析查询词），
但**顺序**错了，导致四个连锁 bug：

| # | 现象 | 原因 |
|---|---|---|
| 1 | 不带参数运行报 `FileNotFoundError` | 先 `load_all` 拿到了 23 个块，紧接着又去读一个**不存在的文件** `data\（全部文件）` → 异常 → `return`，前面白算 |
| 2 | 只给查询词时也报 `FileNotFoundError` | `path = "装饰器"`，**把查询词当成了文件名** |
| 3 | `NameError: name 'n' is not defined` | 块大小只在 `if len(sys.argv) >= 2:` 分支里赋值，单文件模式永远进不去那个分支 |
| 4 | 后面崩在 `c["content"]` | `split_every` 产出**字符串**列表，`load_all` 产出**字典**列表 → 两种结构混用 |

**处理**（关键是第 4 条，它让后面所有代码一行都不用改）：

```python
# ① 先定数据源
if args and os.path.isfile(args[0]):
    ...                          # 单文件模式
    rest = args[1:]
    source_name = os.path.basename(path)
else:
    ...                          # 全目录模式
    rest = args                  # ← 参数左移，让后面的解析只写一遍

# ② 再解析 n 和 query（只写一遍）
if rest[0].lstrip("-").isdigit():     # .lstrip("-") 是为了能识别负数
    n = int(rest[0]); query = rest[1] if len(rest) >= 2 else None
else:
    query = rest[0]

# ③ 统一数据结构 —— 单文件也包成字典
t = [{"source": source_name, "content": c} for c in split_every(m, n)]
```

**教训**：**解析命令行的正确姿势是"先定数据源，再把参数左移"。**
`rest = args[1:]` 这个"左移"动作让后面的解析逻辑只写一遍，
而不是在两个分支里各写一份（两份必然有一份先腐烂）。

**还有第 ③ 条**：`agent()` / `build_index()` / `search()` 都只认字典列表。
**只要喂进去的形状一样，上层一行都不用改。** 这就是"统一数据结构"的价值。

### 14. GBK 控制台遇到 emoji 就崩

**现象**：
```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705' in position 0
```

**原因**：Windows 中文版 PowerShell 默认代码页是 GBK（cp936），
emoji（✅ ❌）和部分符号不在 GBK 字符集里。

**处理**：
```python
for s in (sys.stdout, sys.stderr):
    try:
        s.reconfigure(encoding="utf-8", errors="replace")
    except (AttributeError, ValueError):
        pass
```
（`try/except` 是为了兼容没有 `reconfigure` 的旧 Python 或已被重定向的流。）

**顺带一个坑**：`.bat` 批处理文件里的中文也会乱码——
因为 cmd 按 GBK 解析 `.bat`。最终改成**`.bat` 只放纯 ASCII 的启动命令，中文菜单全部移进 Python**，
并且文件必须存成 **CRLF** 换行。

**教训**：**在中文 Windows 上做 CLI，输出编码是必须主动处理的一等公民**，
不是"以后再说"的细节。

### 15. 子进程捕获管道会炸 `UnicodeDecodeError`

**现象**：
```
UnicodeDecodeError: 'gbk' codec can't decode byte 0x82 in position ...
```

**原因**：用 `subprocess` 捕获另一个 Python 进程的输出时，
父进程默认按系统编码（GBK）解码子进程的 stdout，而子进程输出的是 UTF-8。

**处理**：**写文件而不是走管道**——让子进程把结果写到临时文件，父进程用 `utf-8` 读。
比折腾 `encoding=` 参数可靠。

### 16. TSV 的 UTF-8 BOM 让列名多一个字符

**现象**：
```
KeyError: '\ufeff日期'
```

**原因**：用 Excel 存过的 CSV/TSV 会带 UTF-8 BOM（`\ufeff`），
它粘在**第一个列名**前面，肉眼完全看不出来。

**处理**：读带 BOM 的文件一律用 `encoding="utf-8-sig"`（它会自动吃掉 BOM）。

**教训**：报 `KeyError` 说列名"不存在"、但那个列名明明就在文件里时，
**第一个怀疑对象就是 BOM 或首尾空白**。用 `repr()` 打印出来看。

### 19. FastAPI线程池调用SQLite跨线程报错

**现象**：
网页表单提交后，后台不崩溃但无法创建会话，日志打印：
```
SQLite objects created in a thread can only be used in that same thread.
```

**原因**：
Python的sqlite3默认开启`check_same_thread`校验，只允许在创建连接的线程中使用连接。
而FastAPI对普通`def`路由会自动放到独立线程池执行，连接在主线程模块加载时创建，请求在工作线程执行，就会触发校验失败。

**处理**：
创建连接时显式添加参数关闭线程校验：
```python
conn = sqlite3.connect(DB_PATH, check_same_thread=False)
```
单人本地工具、没有高并发写的场景下，这个方案简单可靠。

**教训**：单线程下运行正常的代码，接入Web线程池后要优先检查线程安全问题，这类问题静态读代码不会暴露，只有真实请求才会触发。

### 20. 命令行打印函数直接给前端用，导致列表不显示

**现象**：
后端代码正常、数据库里有数据，但是页面始终不显示历史会话块，没有报错。

**原因**：
原来的`list_sessions`是命令行专用函数，只负责排版打印内容，没有写return返回值，前端拿到的是None，模板的if判断为假就自动隐藏了整块区域。

**处理**：
不修改原有命令行函数，在app.py里单独写一个Web专用查询函数，直接返回结构化字典列表，两个函数各司其职，互不影响。

**教训**：复用函数前先看它的返回值和设计用途，打印副作用和数据返回是两回事，不能只看函数名就直接调用。

### 21. 删除函数后没改调用，导致500内部错误

**现象**：
清理代码删掉了临时新增的函数，刷新页面直接显示Internal Server Error。

**原因**：
app.py里还保留着对已删除函数的调用，模块导入后触发AttributeError，属于修改代码时漏改引用。

**处理**：
把所有调用替换成app内部的本地函数，统一入口，避免依赖临时函数。

**教训**：删除函数前要全局搜索所有引用点，改完先做语法和导入测试，再刷新页面验证。

## 六、无限循环

### 17. 保护条件写漏一半 → 死循环

**现象**：
- `split_every('abc', -1)` 无限循环
- `split_overlap('abcd', 2, 2)` 无限循环（`overlap == n`）

**原因**：
```python
if n > 0:              # ← 只检查了 n
```
`split_overlap` 的步进是 `n - overlap`。**`overlap == n` 时步进为 0，指针永远不动。**

**处理**：保护条件必须是
```python
if n > 0 and n > overlap:
```

**教训**：**写循环时问自己"指针一定会前进吗"。**
只检查参数不为零是不够的——要检查**步进量**不为零。

（我当时用"子进程 + 超时"来确认死循环，而不是干等——**测试无限循环要给超时**。）

---

### 18. 空字符串也被切出一块

**现象**：`split_overlap('', 3, 1)` 返回 `['']` 而不是 `[]`。

**原因**：`while` 的条件在空串时也满足一次。

**处理**：
```python
if i + overlap != len(s) and len(s[i:]):
    result.append(s[i:])
```

**教训**：**空输入是最容易漏测的边界。**
写完切分类函数，先跑一遍 `''` / `'a'` / 刚好等于 n / 比 n 小一点，这四个用例能抓到大部分问题。

---

## 附：这些坑的共同规律

回头看，18 个坑其实只有五类：

| 类型 | 例子 | 防御办法 |
|---|---|---|
| **缩进 / 作用域**（不报语法错，只让代码静默失效） | #1 #4 #5 #6 | **看输出对不对**，不能只看"没报错" |
| **测量方法错了，却当成被测对象错了** | #7 #8 | 结果"看起来很糟"时，**先怀疑测量** |
| **"数个数"和"数宽度"混用** | #9 | 用 `dwidth()`，永远不用 `len()` 排版 |
| **顺序错了**（必须先做的事做晚了） | #11 #13 | 加载词典→分词→索引；先定数据源→再解析参数 |
| **静默失败**（不报错，只是结果变差） | #11 #12 #16 | 改任何检索参数后，**跑一遍固定测试集对比** |

**最值钱的一条**：**"没报错"和"是对的"是两件事。**
#1（轨迹表空）、#6（只查了 1/3 却报 0 违规）、#12（术语表静默无效）
都属于"程序跑通了，但结果是错的"——**只有主动看输出、主动测量才能发现。**
