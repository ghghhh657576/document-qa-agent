## 版本 A：完整版（4 条，推荐）

**文档知识库问答 Agent（RAG + Function Calling）** | Python · FastAPI · SQLite · jieba · BM25 · DeepSeek API | 2026.10-11

- 独立实现检索增强问答 Agent（**单文件 759 行，仅 3 个第三方依赖**），**手写 Function Calling 循环而非接入 LangChain**：模型自主决定检索时机与查询词（实测会主动换措辞发起二次检索），支持多工具调用与最多 5 步推理；单次问答 3~6s，成本 ¥0.007~0.013。
- 构建 BM25 中文检索层：**标点感知切分**把"块内切断词"比例从 41% 降至 0%（n=500，边界切断口径），配合 239 行停用词表修复虚词干扰（修复前查询"完全不存在的词"得分 6.42，反而高于真实查询"异步"的 2.15）。
- **以严格 top-1 准确率做 A/B 实测，发现手工术语表方案零收益（6/6 vs 6/6）并主动否决**——根因是 BM25 的 IDF 已编码"稀有词更重要"，叠加权重属重复计数、反而淹没区分度信号；同理证伪了"引用内容一致性校验"方案（字符重合度仅 4%~9% 且全为误报，因模型是改写式引用）。
- 设计四道输入防御（工具白名单 / JSON 解析兜底 / 参数空值校验 / 引用校验）与调用链 tracing（逐步记录 token、缓存命中、耗时，CJK 宽度感知排版）；引用校验失败时把**本次真实检索过的块号列表回灌**模型自我修正，实测 5 个查询 0 违规；借助 tracing 定位到 Agent 输入 token 随对话轮次阶梯增长（461→1856）是成本高于单轮问答的根因。
- 扩展 FastAPI 网页应用（不引入前端框架）：**sid 定位会话 + SQLite 存储历史**实现多轮对话持久化，支持历史会话列表、续聊与删除（POST + 302 重定向避免重复提交）；修复线程池跨线程调用报错（`check_same_thread=False`）。

```
1. 每个数字都要能当场解释怎么测的
   ✗ "性能提升 50%"（没测过）
   ✓ "切断词比例 41.1% → 0.0%（n=500，76 个朴素块里 44 个切中词 → 0 个）"
   
   面试官一定会问"这个数怎么来的"。答不上来的数字是负分。

2. 宁愿少写一条，也不要写"实现了 XXX"这种没有信息量的
   ✗ "实现了 RAG 检索和 Agent 工具调用，熟悉 LangChain"
   ✓ "手写 Function Calling 循环而非接入 LangChain"
   
   前者任何人抄一遍教程都能写，后者说明你知道框架替你做了什么。

3. "否决方案"比"实现功能"值钱
   大部分人写的是"我加了 XX 功能"。
   你能写的是"我加了 XX，测出来没用，所以删了"——这才叫工程判断。
```

## 面试预判：一定会被追问的问题

### Q1：「为什么不用 LangChain？」（**必问**）

> **因为我的瓶颈不是"搭起来"，是"搞懂里面发生了什么"。**
>
> 我试过先学 LangChain，但发现以我当时的水平，用它搭出来的东西我能跑通、却说不清每一步为什么这么走。所以改成手写一遍循环——手写之后我才真正理解了几件用框架时不会注意的事：
>
> - **模型返回的 `tool_calls` 参数是 JSON 字符串，不是字典**，必须 `json.loads`，而且模型可能给出非法 JSON
> - **`messages` 必须累积**，每一轮都要把全部历史重发。这就是 Agent 贵的原因——我用 tracing 量过，输入 token 从第 1 轮的 461 涨到第 2 轮的 1856
> - **工具结果要以 `role: "tool"` + 配对的 `tool_call_id` 追加回去**，配对错了模型就乱了
>
> 我不是反对框架。**是先用最笨的办法走一遍，才知道框架在替我做什么、以及它在哪些地方替我做错了。**

### Q2：「你这个检索效果怎么样？」（**必问**）

> 严格 top-1 准确率 **6/6**（我人工标了 6 个查询的正确答案块）。
>
> 但我更想说的是**我测过什么没用的**：我手工从三门课件里提了 35 个术语做词典，测下来带与不带都是 6/6，**零收益**。原因是 BM25 的 IDF 项已经编码了"稀有词更重要"，我再叠一层是重复计数。所以我把它删了，只保留成可选。
>
> 还有一次是"引用内容一致性校验"——我用字符重合度做，跑出来只有 4%~9%，看起来模型全在瞎引。但我意识到那是**误报**：那 80 个字是模型自己的过渡句，原文引用在标记后面；而且模型是改写式引用，字符级比对必然不匹配。**所以我砍掉了这个方案，而不是去调它的阈值。**

### Q3：「怎么保证模型不瞎编？」

> 分两层看：**出处**和**内容**。
>
> **出处**我做到了：回答里每个 `块 #N` 都会校验两件事——① 这个块号在知识库里存在吗 ② 它在**这一次**检索里真的返回过吗。第二条才是关键，因为模型最常见的幻觉不是编号越界（它是从资料块头抄的），而是**引一个存在、但这次没检索过的块**——那种引用看起来完全合理，不校验根本抓不出来。
>
> 校验失败时我会把**本次真实检索过的块号列表**回灌给它让它重答，只给一次机会防止死循环。实测 5 个查询 0 违规。
>
> **内容**我做不到，而且我明确没做。想校验"引用的那句话在原文里有没有"只能靠另一个模型拿原文核对，成本翻倍还可能判错。**所以引用校验的定位很清楚：保证出处真实，不保证内容真实。**这个边界我在 README 里主动写了。

### Q4：「759 行写了多久？最难的地方是哪？」

> 两周（课余时间）。最难的不是写功能，是**发现"跑通了但结果是错的"**。
>
> 有三个坑都属于这一类：
> - 引用校验的 `return` 缩进落在 `for` 循环里，**只查了 3 处引用中的第 1 处，却报告"0 违规"**——"没问题"和"没检查"长得一模一样
> - 轨迹表的 `trace.append` 缩进落进了 `except` 分支，而那行是死代码，**表格里一条记录都没有**
> - 表格排版用 `len()` 算宽度，但 `len("模型决策")` 是 4、它占 8 列，**表头和数据行差 11 格**
>
> 共同点是**都不报错**。后来我养成了一个习惯：任何"辅助功能"（日志、校验、统计）上线后，**第一件事是看它的输出对不对**，而不是看程序有没有崩。

### Q5：「如果接着做，下一步做什么？」

> 两件事，按顺序：
>
> 1. **公开部署**——Web 端全功能（多轮对话、历史会话管理、删除）已经在本机跑通，接下来处理公网链接、鉴权、限流。
> 2. **混合检索**——BM25 强在精确术语（查"装饰器"准），向量强在语义近义（查"怎么复用代码"也能召回装饰器那段）。**两者不是替代关系**，我先把 BM25 做到可测量当基线，再加向量做融合，这样能说清"加它到底带来了多少提升"。

### Q6：（如果被问）「就一个课程资料问答，是不是玩具？」

> 规模是小的，但**里面每一个决策都是我测出来的，不是抄的**。我可以给你讲：
>
> - 为什么块大小选 500（标点感知切分下边界切断比例 0%，n=300 时是 0.9%）
> - 为什么停用词表是 239 行（去重 237 个）而不是"常见的那几十个"（我按词频表逐个判的，`'的'` 454 次该删，`'项目'` 105 次绝对不能删——**判断标准是区分度不是频次**）
> - 为什么索引和查询必须共用一个 `tokenize` 函数（我改了 jieba 词典后所有分数变 0，因为索引用的旧分词、查询用的新分词）
>
> 我也知道自己缺什么：**没有并发、没有真实用户、数据量只有 73 个块**。这些是我下一步要去实习里学的。

### Q7：「Web 端多轮对话怎么实现的？遇到过什么坑？」

> 用 **sid 定位会话 + SQLite 存储历史**。核心是理解大模型和 HTTP 都无状态：每次请求后端根据 sid 查出这条会话的全部历史，和当前问题一起完整重发给模型，所以模型看起来"记得上下文"，其实是我每次在帮它复习历史。
>
> 开发时踩过一个真实的坑：FastAPI 的普通 `def` 路由会跑在线程池里，而 Python 默认的 SQLite 连接只允许在创建它的线程使用，一提交表单就报 `SQLite objects created in a thread can only be used in that same thread`。加 `check_same_thread=False` 解决——单人本地工具没有高并发写，这个方案简单可靠，但我知道正式高并发场景要换连接池。

### Q8：「删除会话功能，为什么用 POST 不用 GET？删完为什么跳转？」

> 删除是修改数据的操作，GET 会被浏览器缓存、预加载，甚至被插件自动请求，可能误删；POST 必须用户主动触发表单才执行。
>
> 删完后用 302 重定向回首页，遵循 Post/Redirect/Get 模式：如果 POST 直接返回页面，用户按 F5 刷新会触发重复提交删除；重定向后刷新只会重新请求首页，不会重复执行删除。删除时先删消息再删会话，避免留下没有对应会话的孤儿数据。

### Q9：「从头到尾讲一遍你这个 RAG 的完整流程」（**高频**）

> 一条分层流水线（第 0~4 层），顺序固定：
>
> 1. **数据层**：读本地 txt，按标点感知切块（每块带块号+文件名），启动时一次性加载成 73 块
> 2. **检索层**：问题用 jieba 分词、过滤 239 行停用词（去重 237、另叠加 6 个疑问词），BM25 给所有块打分，取最相关的喂给模型
> 3. **Agent 层**：把检索结果拼进 prompt，手写 Function Calling 循环（最多 5 步），模型可自主调用检索或出题工具；拿到回答后做两级引用校验，不通过就回灌真实块号让它重答一次
> 4. **应用层**：回答落库，返回给用户；命令行和网页共用同一套核心逻辑，网页端多加了多轮、历史会话、执行轨迹可视化
>
> 关键点：检索、执行、校验、纠错都在我的代码里，模型只负责决策，不是"调一次接口就完事"。

### Q10：「为什么用 BM25 而不是向量检索？」（**高频**）

> 核心区别是匹配逻辑：**BM25 是字面/关键词匹配，向量是语义匹配**。
>
> 我的知识库是技术文档，专有名词多、提问围绕明确知识点，BM25 的精确关键词匹配已经够用，而且纯本地运行、零额外成本、可解释性强。它的短板是处理不了同义语义（问"怎么复用代码"，文档写"装饰器封装"就召不回），所以后续规划加向量做混合检索，用同一批测试题对比准确率，再决定怎么融合。
>
> 我不说"小体量所以用 BM25"，因为体量不是决定因素，匹配逻辑才是。

### Q11：「这个项目用了 AI 辅助，你怎么证明这些代码你真的懂？」（**必问，最关键**）

> 我诚实说分工：核心逻辑——切块、检索、Agent 循环、引用校验——是我自己写并且完全理解的；输入校验的兜底代码、前端 HTML 是 AI 辅助完善的。
>
> 但"AI 辅助"不等于"我不懂"，我有三件事可以证明理解深度：
>
> 1. **能脱稿写核心函数**：切块、分词、BM25 检索、工具调用循环这几个函数，不看书能默写出来，能解释每个参数为什么这么设计
> 2. **设计决策是自己测出来的**：术语表零收益、引用内容校验全是误报、向量不直接替换 BM25——这三个"否决"都是我拿实测数据做的判断，AI 只能帮我写代码，不能替我做工程决策
> 3. **踩过的坑能讲清根因**：SQLite 跨线程、引用校验 return 缩进在 for 里只查了第 1 条、trace.append 落进 except 死分支——每个坑我都能说清现象、原因、怎么定位的
>
> 我用 AI 提高写代码的速度，但理解每一行为什么这么写，这个是我自己补上来的。

### Q12：「切块大小为什么选 500？」（**高频，考工程细节**）

> 不是随便拍的，是实测出来的。朴素按长度硬切，会有 41% 的块边界把词切断；改成"优先在句末标点处断开"后，切断比例降到 0%。我还对比了 n=300，切断比例是 0.9%，比 500 略高。所以选 500 是在"切断词率低"和"单个块上下文完整"之间取的平衡。
>
> 面试官问这个，想听的不是数字，是你有没有真的测过、有没有比较意识，而不是抄了个默认值。
