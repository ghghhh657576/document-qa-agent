> 更新时间：2026-11-22

## 第 1 题：介绍一下这个项目

### 标准答案框架（按分层结构讲）

这个项目是一个本地文档问答 Agent，把课件资料喂进去，用自然语言提问，基于资料回答并标注来源，资料里没有就拒答。整体分层（第 0~4 层）：



1. **数据层**：读取本地 txt 文档，按标点感知切块，每块带编号和文件名

2. **检索层**：jieba 分词 + 停用词过滤 + BM25 打分，取最相关的几个块

3. **Agent 层**：手写 Function Calling 循环，模型决定是否调用出题工具；回答后做引用校验

4. **应用层**：命令行 + FastAPI 网页，支持多轮对话、历史会话管理、删除会话

核心亮点是：不是 "调一次模型接口"，而是手写工具调用循环，模型只负责决策，执行、校验、纠错都在本地代码里。

### 易错点



* 不要按 "先做了什么、再做了什么" 的流水账讲，要按分层结构，面试官好抓重点

* 分工表述要诚实：核心逻辑（切片、检索、Agent 调用）自己写，输入校验、前端 HTML 是 AI 辅助完成。诚实说分工 + 证明自己写的部分真懂，比笼统说 "全是我写的" 更稳

## 第 2 题：为什么用 BM25，不用向量检索？

### 标准答案

核心区别是匹配逻辑不同：



* **BM25**：字面 / 关键词匹配，问题里出现 "装饰器"，文档里也要有 "装饰器" 才能匹配，靠词频和稀有词打分

* **向量检索**：语义匹配，即使字面完全不同，问 "怎么复用代码"，文档写 "装饰器封装" 也能靠语义相似度找到

我选 BM25 的理由：



1. 知识库是技术文档，专有名词多，提问围绕明确知识点，精确关键词匹配已经够用

2. 纯本地运行、零额外成本、可解释性强，方便调试和读懂完整链路

3. 短板是处理不了同义语义，所以后续规划加向量做混合检索，用测试集对比准确率再决定融合方式

### 易错点



* 别说 "小体量所以适合 BM25"，体量不是决定性因素，**匹配逻辑**才是

* "字面匹配 vs 语义匹配" 这句话一定要说出来，这是面试官最想听的



***

## 第 3 题：Function Calling 是怎么实现的？

### 标准答案

Function Calling 是给大模型发 "工具说明书"，让它能主动调用本地写好的函数，而不是只会生成文字。

我的项目里给模型开放了出题工具，完整流程：



1. 提前告诉模型：「有个工具叫 generate\_quiz，参数是主题 topic 和题数 count」

2. 用户要求出题时，模型不会自己编题目，而是返回结构化的工具调用请求，包含工具名和参数（比如 topic = 装饰器、count=5）

3. 本地代码解析参数，执行 do\_generate\_quiz 函数，基于检索到的资料真正生成题目

4. 把结果以固定格式回传给模型，模型再整理成最终回答

和普通问答的区别：普通问答模型只能生成文字，遇到需要精确执行的内容容易瞎编；Function Calling 让 Python 执行确定性逻辑，结果更可控。

### 易错点（重点，这次模拟在这里混淆过）



* **RAG ≠ Function Calling**，一定要区分：


  * RAG = 把资料检索出来喂给模型，解决 "回答没有依据"

  * Function Calling = 让模型调用工具，解决 "模型只会说、不会动手执行"

* 减少幻觉主要是 RAG 和引用校验的功劳，不是 Function Calling

* 回答时要点出 "结构化参数、解析、回传"，体现理解消息流转



***

## 第 4 题：引用校验是怎么做的？

### 标准答案

引用校验分两级：



1. **第一级：块号是否存在**。总共 73 块，编号 0\~72，模型引用第 99 块就判定不存在

2. **第二级：块号是否本次真的检索过**。模型只能引用这次确实喂给它的资料，不能引用一个虽然存在、但这次没检索到的块

校验不通过时，把错误信息和本次真实检索过的块号列表一起回灌给模型，让它重新回答，只给一次机会。

### 易错点



* 两级校验都要说出来，第二级 "必须是本次检索过的块" 才是精髓

* 别把 trace 说成 "记录错误引用"。trace 记录的是执行轨迹（token、耗时、缓存命中率、成本），引用违规的处理是回灌重答，两件事别混

## 第 5 题：Web 端多轮对话是怎么实现的？sid 起什么作用？

### 标准答案

核心前提：大模型和 HTTP 都是无状态的，每次请求模型 "失忆"，不会自动记住之前的对话。

多轮对话的本质不是模型记住了，而是：



1. 浏览器通过隐藏的 sid 字段，每次提交都把当前会话编号传回后端

2. 后端根据 sid 从数据库查出这条会话的全部历史消息

3. 把历史消息和当前问题一起，完整地重新发给大模型

4. 所以模型看起来 "记得上下文"，其实是每次都在帮它复习历史

sid 的作用：定位 "这一串历史消息属于哪个会话"。首次提问时数据库自动生成新 sid，续聊时 sid 保持不变，通过隐藏字段自动回传，不需要用户手输；点 "开启新对话" 就清空 sid 重新生成。

### 易错点



* "无状态" 这个灵魂概念一定要说出来，这是多轮对话和 HTTP 问题的万能钥匙

* 强调 "每次把完整历史重发一遍"，而不是 "模型记住了"

## 附：三个最容易混淆的概念（一句话区分）



| 概念               | 一句话         | 解决什么问题      |
| ---------------- | ----------- | ----------- |
| RAG              | 先检索资料再喂给模型  | 回答没有依据、减少幻觉 |
| Function Calling | 让模型调用本地工具   | 模型只会说、不会执行  |
| 引用校验             | 验证模型引用的出处真实 | 防止编造不存在的来源  |
